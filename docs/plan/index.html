Talos GitOps migration — the working plan

Decisions are locked (see ADRs). Seven phase runbooks below; each is a checklist you can follow end-to-end. Checkbox state persists in your browser.

R1

Repeatability. Fresh server → production, data restored, in < 4 h.

R2

PR-merge deploys. Merging on GitHub is the only deploy action.

R3

Elastic topology. Node counts are OpenTofu variables (CP 1↔3, workers N).

R4

One repo. New tofu/ + k8s/ dirs beside the existing tree.

Exposure model: nothing is public. All services are LAN-only or reached via your own VPN (wg-easy, kept on its VM — ADR 0005). Certificates still use Let's Encrypt DNS-01 wildcards, which never require an open port; no port-forwards exist on the UCG-Fiber.

Talos Image Factory

The image spec — decide once, upgrade in place forever

First, the pressure release: a schematic choice is not permanent. Changing extensions later is an in-place talosctl upgrade --image factory.talos.dev/installer/<new-id>:<version> — the node reboots into the new image with data intact. No reinstall, ever. So choose a sensible baseline and move on.

# schematic.yaml — same schematic for all nodes
customization:
  systemExtensions:
    officialExtensions:
      - siderolabs/qemu-guest-agent
      - siderolabs/iscsi-tools
      - siderolabs/util-linux-tools
# Upload once; the returned ID is content-addressed — record it in tofu vars
curl -s -X POST --data-binary @schematic.yaml \
  https://factory.talos.dev/schematics
# → {"id":"<SCHEMATIC_ID>"}

# Boot ISO (Phase 1) and installer image (machine config):
# https://factory.talos.dev/image/<SCHEMATIC_ID>/<VERSION>/metal-amd64.iso
# factory.talos.dev/installer/<SCHEMATIC_ID>:<VERSION>

Why these three

  • qemu-guest-agent — required. Proxmox (and the tofu provider) uses it for IP discovery and clean shutdown.
  • iscsi-tools + util-linux-tools — not needed by local-path today; a few MB of insurance that keeps iSCSI-based storage (Longhorn et al.) bootable without an upgrade cycle if you ever experiment.

Deliberately excluded

  • amd-ucode — microcode is applied by the Proxmox host; useless inside a VM.
  • amdgpu firmware — only needed on the one worker that would receive iGPU passthrough (Phase 5), and only if you go that route; apply it then, to that node only, via per-node in-place upgrade.
  • zfs / btrfs / nvidia / wifi firmware — guest disks are virtual, no such hardware in the VM.

Everything else is machine config, not image

Static IPs, the control-plane VIP, cni: none + proxy.disabled (for Cilium), kubelet extraMounts for local-path, install disk — all live in Talos machine-config patches in tofu/, applied without image changes. See Phase 1.

NVMe endurance

Write-amplification playbook

The design already makes the two biggest cuts: one etcd member (ADR 0003) and no replicated block storage (ADR 0004). The rest is host and workload hygiene, applied in Phase 1/Phase 6:

Proxmox host (ZFS)

  • ▸ zfs set atime=off rpool — kills a metadata write per file read
  • ▸ zfs set compression=zstd rpool — compressed blocks = fewer bytes physically written (lz4 if CPU-shy)
  • ▸ Keep zvol volblocksize at the PVE default (16K); don't shrink it
  • ▸ sync=standard — never always (2× writes), never disabled (lies to etcd)
  • ▸ zpool set autotrim=on rpool + monthly zpool trim rpool
  • ▸ Single node: systemctl disable --now pve-ha-lrm pve-ha-crm — stops constant HA state writes
  • ▸ No swap on ZFS; vm.swappiness=10

VM disks (tofu)

  • ▸ virtio-scsi with discard=on and ssd=1 — guest TRIM reaches the zvol, keeping thin disks thin
  • ▸ iothread=1 for etcd latency (cp-1 disk)

Inside the cluster

  • ▸ Flux: reconcile intervals 10m+ for stable Kustomizations (1m polling churns etcd)
  • ▸ Prometheus: 60s scrape, ~15d retention; skip log-shipping stacks unless you need them
  • ▸ Databases: fewest possible instances; CNPG consolidation is the eventual answer

Watch the wear, don't guess

  • ▸ Baseline now, check quarterly: smartctl -a /dev/nvme0 | grep -E 'Percentage Used|Data Units Written'
  • ▸ Phase 6 adds a smartctl exporter panel in Grafana

Runbooks

Seven phases, strangler-style

Legacy VMs keep serving until each replacement is verified. Every phase ends demo-able. Rough total: 2–3 months of weekends.

Phase 0 — Decisions & scaffold 1 evening

ADRs, SOPS rule for k8s/, CLI tooling, age-key escrow.

Phase 1 — Provision 1–2 weekends

Factory image → tofu → Proxmox VMs → bootstrapped Talos; scale drills.

Phase 2 — Platform core 1–2 weekends

Flux bootstrap, Cilium, cert-manager, ingress, local-path, VolSync, NFS CSI.

Phase 3 — First apps R2 lands

Wave 1 stateless apps, Renovate wiring, CI validation, PR-merge deploys proven.

Phase 4 — Stateful 2–3 weekends

Data-move recipe, n8n/odoo, VolSync schedules, optional CNPG.

Phase 5 — Media & hardware highest risk

NFS media, arr/immich, jellyfin GPU decision, caddy retirement, VM keep-list.

Phase 6 — Observability & DR drill R1 proven

Monitoring, backup automation, offsite copy, the timed rebuild.

Disaster recovery

The < 4 hour rebuild

Preconditions: the Git repo (on GitHub), the age key (escrowed offline — Phase 0), the NAS backup set (restic repos + offsite copy). Media never needs restoring; it reattaches over NFS.

StepTimeWhat happens
1Fresh Proxmox host~30 minInstall PVE, apply host tuning (NVMe playbook), clone repo, load age key
2tofu apply~20 minVMs from factory image → machine configs → bootstrap → kubeconfig
3flux bootstrap~45 minFlux self-installs, decrypts with age key, reconciles cilium → platform → apps
4Data restore1–2 hVolSync ReplicationDestination per app PVC pulls from the NAS restic repo; CNPG replays WAL; media reattaches via NFS
5Verify~30 minDNS, certs, app health, one restore spot-check per data tier

Permanent VMs (wg-easy, ADR 0006 keepers) restore via the existing Ansible + volume-backup flow, in parallel. Full drill with a timer: Phase 6.
